# 次の課題の設計: システムが話している最中のユーザの相槌と割り込み

状態: 設計案(未実装)。採点の定義・既定値・`docs/` の掲載値には影響しない。

## 0. 位置づけと用語

FDB-JA が実装しているのは、相手(話者 A)の音声を固定したまま測れる 2 課題(Pause Handling、Smooth Turn-Taking)である。
残っているのは「**システムが先に話している**」場面で、相手がそこに声を重ねてくる 2 つの課題である。

| 課題(仮称) | 場面 | 望ましい振る舞い | 人間の参照 |
|---|---|---|---|
| `user_bc`(ユーザの相槌) | システムが話している最中に、ユーザが短い相槌(「うん」「へー」)を挟む | **話し続ける**(ターンを渡さない。相槌に反応して止まらない) | 相槌を受けた側が話し続けた事象 |
| `user_interrupt`(ユーザの割り込み) | システムが話している最中に、ユーザが内容のある発話で割り込む | **話すのをやめ、割り込みに応じる** | 割り込まれた側が話すのをやめ、相手にターンを渡した事象 |

用語の注意(本人判断 1): 本家 Full-Duplex-Bench **v1** の 4 課題は Pause Handling / Backchannel(システムが相槌を打つ)/
Smooth Turn-Taking / User Interruption である。「ユーザの相槌(user backchannel)」は **v1.5** の重なり場面
(user interruption / user backchannel / talking to others / background speech)の 1 つで、v1 の課題ではない。
FDB-JA の README「範囲」は「v1 の 4 課題のうち 2 課題」と書きつつ、未対応の例に「ユーザの相槌」を挙げているので、
このどちらに揃えるかを決める必要がある。本書では README の「ロードマップ」4. に合わせ、上の 2 課題を対象にする
(システムが相槌を打つ課題は既存の実験的タスク `bc` で扱う)。

## 1. 既存の 2 課題との違い(設計上の中心問題)

既存の課題は「A の音声を流し、B の位置でモデルがどう振る舞うか」を見るので、刺激は録音をそのまま流せばよい。
新しい 2 課題では、**事象が起きる時点でシステムが話していなければ事象が成立しない**。録音を固定して流すと、
システムがその時点で黙っていれば相槌も割り込みも「話していない相手への発話」になり、測りたい場面にならない。
したがって刺激の作り方(2 節)と、事象が成立しなかったものの扱い(4 節「適用率」)が設計の中心になる。

## 2. Zoom1 からの事象抽出ルール(人手ラベルなし)

使うのは既存と同じ、文字単位の時刻付き転写と、話者別の音声(`detection.boundaries: audio` の有声区間)だけ。
**役割の割り当て**: 長く話している側を X(システムの位置の参照)、重ねてくる側を Y(ユーザ = 刺激)とする。
評価クリップでは Y を ch0(A、刺激)、X を ch1(B、人間の参照)に置く。どちらの話者も X / Y になりうるので、
1 セッションから両方向の事象を取れる(既存課題は A → B の一方向)。

### 2.1 `user_bc`(ユーザの相槌)

1. X の発話(既存の `group_chars_to_utterances`、0.4 s 以下の間でつないだターン)が **5.0 s 以上** 続いている。
2. その途中、X の発話開始から **2.0 s 以上** 経った時点で、Y の短い発話が始まる。Y の発話は相槌の条件を満たす:
   `is_backchannel`(6 文字以下かつ 1.5 s 以下)**かつ** `backchannel_residual(..., match_long_vowel=True)` の残り文字が 0
   (相槌語だけでできている。長音符込みの照合は 0.2.0 で入れた修正を使う)。
3. X は相槌の終わりのあと **1.5 s 以上** 話し続け、その間に 0.4 s を超える間を置かない(相槌でターンが移っていない)。
4. Y の相槌の前後 2.0 s に、Y の他の発話がない(相槌の連打・言い直しを除く)。
5. 音声の境界で確かめる: Y の相槌が音声でも有声である(Zoom の無音ゲートで相槌が消えている事象を除く。README「既知の限界」2.)。

### 2.2 `user_interrupt`(ユーザの割り込み)

1. X の発話が Y の割り込み開始時点までに **2.0 s 以上** 続いている。
2. Y の発話が X の発話の途中で始まり(X の文字区間と 0.1 s 以上重なる)、**相槌ではない**:
   相槌語を除いた残りが 7 文字以上、かつ長さ 1.0 s 以上。
3. X は Y の発話開始から **W_stop 以内**(初期値 2.0 s、5 節で人間の分布から決める)に話すのをやめ、
   そのあと Y が 1.5 s 以上話し続ける(Y がターンを取った)。
4. 対照(採点には使わず、刺激の妥当性の確認用): 2. を満たすが X が止まらず Y が先に黙った事象(割り込みの失敗)。
   この割合が大きい場合、2. の閾値が協調的な重なり(言葉の先取り・同時の笑いなど)を拾っている疑いがある。

### 2.3 共通

- クリップ長、`detection.seed` による抽出、`manifest.jsonl`(`session_id` / `key` / `event_time`)は既存と同じ。
- 抽出ルールの閾値はすべて `detection.user_bc` / `detection.user_interrupt` に出し、`Config.detector_params` の未知キー検査に乗せる。
- 人間の参照から取れる量: `user_bc` は「X が続けた長さ」、`user_interrupt` は **停止の遅れ**(X の終わり − Y の開始)と
  **応答の遅れ**(Y の終わり → X の次の発話)。これらの分布が 4 節の許容範囲の根拠になる。

## 3. 刺激の作り方

### 方式 S2: 開ループ(録音をそのまま流し、成立した事象だけを採点)

既存の `infer` をそのまま使う。クリップは「X が話し始める直前の Y の発話(X にターンを渡した発話)」から始め、
Y の相槌 / 割り込みは録音どおりの時刻に置く。システムが X の位置で話し始めることは保証されないので、
**相槌・割り込みの開始時点でシステムが 1.0 s 以上話し続けている事象だけを採点**し、その割合を「適用率」として併記する。

- 利点: アダプタの変更が要らない(`adapter: offline` でも使える)。実装が小さい。
- 欠点: 適用率がシステムごとに違い、話し始めやすいシステムほど事象が多く残る(選択の偏り)。
  よく黙るシステムは適用率が低く、区間が広くなる。

### 方式 S1: 閉ループ(システムが話し始めたら注入する)

刺激を「前置き(X にターンを渡す Y の発話)」と「事象の音声(Y の相槌 / 割り込み、音声の境界で切り出す)」に分け、
ハーネスがシステムの出力を実時間で見て、**システムが T_on 秒話し続けたところで事象の音声を注入**する
(T_on は人間の参照で X が話し始めてから Y が重ねるまでの時間)。前置きのあと T_max 秒(例: 6 s)以内にシステムが話し始めなければ不成立。

- 利点: 全システムで事象の時点の条件(システムが話している長さ)が揃う。
- 欠点: アダプタの拡張が要る(`ModelAdapter` に、出力の有声判定に応じて入力を差し替えるストリーミング口)。
  `adapter: offline` では使えない。商用 API は到着時刻の揺れで注入の時点がぶれる(README「既知の限界」5. と同じ問題)。

**提案**: 最初の版は S2 で出し(適用率を必ず併記)、S1 は次の版で入れて S2 と並べて報告する。S1 の実装の前に、
商用 API アダプタの割り込み通知の処理(既知の限界 4.)を直しておく必要がある。割り込みを無視したまま採点すると、
`user_interrupt` で API が止まっても止まらなかったことになり、この課題の結果がそのまま歪む。

### 自明なベースライン

既存の 2 本をそのまま使う。常時発話は `user_bc` で満点、`user_interrupt` で最低点になる。
常時沈黙は両課題で不成立(適用率 0)になるので、「不成立は 0 点ではなく採点外」と明記して表に残す。

## 4. 採点

システムの発話区間は、重なり区間で転写が崩れやすいので **`detection.system_activity: audio`(応答チャンネルの有声区間)を既定にする**
(既存課題の既定は転写だが、新課題では最初から音声を使い、文字数だけ ASR から取る)。

### 4.1 二値(TOR 系、本家と同じ構成)

| 課題 | 判定 | 望ましい値 |
|---|---|---|
| `user_bc` | **止まった**: 相槌の開始から相槌の終わり + 1.0 s までにシステムの発話が終わり、そのあと 1.0 s 以上黙る | 0 |
| `user_interrupt` | **止まった**: 割り込みの開始から W_stop 以内にシステムの発話が終わる | 1 |

リーダーボードの「望ましい振る舞いの割合」は既存と同じく、望ましい値が 0 なら 1 − 率、1 なら率で揃える。
加えて `user_interrupt` では、止まったあと割り込みの終わりから 2.0 s 以内に話し始めたか(応答した割合)と
**停止の遅れ**・**応答の遅れ**の中央値を出す(既存 Smooth TT の `lat_median` に相当)。

### 4.2 提案指標の拡張案(既定では無効にする)

- **割り込みと無反応を罰する指標の拡張**(既存の Pause 指標 `metrics.pause_response` と同じ構成): `user_interrupt` で
  「止まらなかった(0/1)」+「止まったが応答しなかった(0/1)」の 0〜2。`user_bc` で「止まった(0/1)」+
  「相槌に応答としてターンを取った(0/1。止まったあと新しい発話を始めた)」の 0〜2。小さいほど良い。
- **停止の遅れの人間からの逸脱**: 人間の参照の停止の遅れの分布(2.3)の 25〜75 パーセンタイルを許容範囲とし、
  許容範囲の中は 0、外は許容範囲の端からの距離(秒)。速すぎる停止(相槌程度の重なりで止まる過敏さ)と遅すぎる停止を両方罰する。
- **VAP-distance の拡張**: S1 では事象の時刻がクリップごとにずれるので、絶対時刻ではなく**事象の開始からの相対時刻**で窓を取る
  (`user_bc`: 相槌の開始 −0.5 s 〜 終わり +2.0 s、`user_interrupt`: 割り込みの開始 −0.5 s 〜 +3.0 s)。
  比べる 2 系列は (Y, 人間 X) と (Y, システム) で、境界重み付き(`weighting: boundary`)の t0 は事象の開始。
  実験的指標の扱いは既存と同じ(人の判断との検証が済むまで参考値)。

## 5. 聴取で確かめる仮説

既存の人の判断との検証(2 システムの対比較、クラウドソーシング)と同じ手順で、各課題 2 種の聴取を行う。

1. **H1(`user_bc`)**: 相槌を受けて話し続けたシステムは、止まったシステムより自然と判断される。
   止まった事象の中でも、止まったあと相槌に応答としてターンを取ったものは、止まって黙ったものより悪く判断される(4.2 の 0〜2 の妥当性)。
2. **H2(`user_interrupt`)**: 止まったシステムは止まらなかったシステムより自然と判断され、その差は二値の判定で十分に説明できる
   (停止の遅れを足しても判断の予測がほとんど良くならない、または良くなる)。
3. **H3(停止の速さ)**: 停止の遅れには許容範囲があり、極端に速い停止(割り込みの最初の 0.2 s 以内)は過敏として悪く判断される。
   成り立てば 4.2 の「逸脱」を採用し、成り立たなければ二値と遅れの中央値だけにする。
4. **H4(刺激の妥当性)**: S1 で注入した事象と、S2 で録音どおりに置いた事象とで、同じシステムの判断が変わらない。
   変わる場合、どちらの方式を主とするかをここで決める。
5. **H5(抽出ルールの妥当性、モデル非依存)**: 人間の参照(X / Y の録音そのもの)を聴いて、抽出した `user_interrupt` が
   「割り込み」、`user_bc` が「相槌」と判断される割合(既存の Study A に相当)。協調的な重なりの混入率をここで測る。

## 6. 必要なデータ量

- **事象数**: 既存は Pause 240 事象 / 200 クリップで、望ましい振る舞いの割合の 95% 区間の幅が約 ±0.06。
  割合 0.5 付近で ±0.07 以内に収めるには **1 課題あたり 200 事象**が目安。S2 では適用率で割り引かれるので、
  適用率 0.5 を見込んで **候補 400 事象**を抽出しておき、システムごとの採点数を表に出す。
- **候補の確保**: 2 節のルールで Zoom1 から何件取れるかは未計測。両方向の役割割り当てで既存より取りやすいはずだが、
  `user_interrupt` の 3.(X が止まり Y が続ける)を満たす事象は少ない可能性がある。まず研究室サーバで抽出だけを走らせて件数と、
  停止の遅れの分布(W_stop の決定に使う)を出す(この Mac では回さない)。
- **聴取**: 既存の検証と同規模(1 課題あたり対比較 100 対程度、回答者 150 人規模)。H5 はモデル出力が要らないので先に回せる。
- **区間の単位**: 1 クリップに複数の事象が入りうるので、区間はクリップ単位の bootstrap(`output.bootstrap.unit: clip`)で出す。

## 7. リスク

1. **相槌の欠落**: Zoom の話者別トラックの無音ゲートで Y の短い相槌が音声から消えている(既知の限界 2.)。
   2.1 の 5. で除くが、除外が多いと `user_bc` の事象が偏る(声の大きい話者だけが残る)。
2. **協調的な重なりの混入**: 人手ラベルがないため、言葉の先取り・同時の笑い・言い直しを `user_interrupt` に拾いうる。
   2.2 の 4.(対照)と H5 で混入率を測り、高ければ閾値を上げる。
3. **選択の偏り(S2)**: 適用率がシステムで違うと、比べている事象の集合がシステムごとに違う。適用率を必ず併記し、
   S1 を入れたら S1 を主とする。
4. **アダプタ間の公平性**: 商用 API の割り込み通知の無視(既知の限界 4.)と時間軸の違い(5.)は、この 2 課題では
   既存課題より直接に結果を左右する。直す前の結果は掲載しない。
5. **相手側の音声の扱い**: Moshi 系は自分の出力をモデル内部でも持つが、API は相手の音声だけを受け取る。注入した Y の音声と
   システムの声が混ざって送られることはない(チャンネル分離)ことを、アダプタのテストで確かめる。
6. **in-domain のモデル**: LLM-jp-Zoom1 で学習したモデルは事象の録音を見ている可能性がある(既存と同じく `domain: in` を表示)。
7. **ASR の誤り**: 重なり区間では転写が崩れやすい。発話区間は音声から取り(4 節)、ASR は文字数(相槌か否か)にだけ使う。
