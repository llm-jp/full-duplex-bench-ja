# 任意の 2 チャネル録音を測る入口(`fdbja measure`)の設計

状態: 実装済み(`src/fdbja/measurement.py`、`fdbja measure` / `fdbja make-profile`)。採点の定義・既定値・`docs/` の掲載値には影響しない。
検出の既定値は合成信号の単体テストに加えて、実際の録音でも検証した。そこで分かった制約は 8 節にまとめた。
雑音や音漏れのある録音と、長い録音では未確認(8 節、9 節)。

## 0. 位置づけ

FDB-JA のベンチマークは、固定の評価セット(話者 A の音声と、転写から検出した事象)にモデルの応答を録って採点する。
数値を比較できるのはこの固定があるからだが、評価セット・モデルアダプタ・ASR を用意しないと 1 つも数値が出ない。

`measure` はその手前の入口で、**手元にある対話の録音 1 本**(ユーザとシステムが別々のチャネル)からタイミングの統計を出す。
転写・注釈・GPU・追加の依存は要らない。代わりに、事象は録音そのものから検出するので、**出た数値はリーダーボードと比較できない**。
この 2 つを取り違えないことを設計の第一の制約にした(5 節)。

## 1. 入力と出力

| 入力 | 呼び方 |
|---|---|
| 2 チャネルの wav 1 本(既定 ch0 = ユーザ、ch1 = システム) | `measure("rec.wav")`、`--user-channel 1` で入れ替え |
| mono の wav 2 本 | `measure("user.wav", "system.wav")`、`fdbja measure user.wav --system system.wav` |
| numpy 配列とサンプリング周波数 | `measure(x, sample_rate=16000)`(`x` は (サンプル, 2))、`measure(user, system, sample_rate=16000)` |
| ディレクトリ、またはパスの並び | 配下の 2 チャネル wav を名前順に全部測り、録音ごとの値と全体の集計を出す |

音声は再標本化しない(フレーム長をサンプリング周波数に合わせるだけ)。出力は `Measurement`(`stats` / `score` / `recordings` / `events` /
`signature` / `conditions` / `config` / `profile` / `warnings`)で、`print()` で表、`to_dict()` と `--json` で JSON になる。

出力は 3 つの層に分けて示す。表示では層ごとに見出しを付け、JSON では `layers` に各層のキーと注記を入れる(値のキーは従来のまま)。

| 層 | キー | プロファイル | 何を表すか |
|---|---|---|---|
| (a) 記述統計 | `stats` の全部 | 不要 | 録音から検出した事象の数え上げ。良し悪しは述べない |
| (b) 人の規範からの外れ | `score.latency_in_tolerance_rate`、`score.latency_deviation_mean`。内訳は `score.turn_end_no_response_rate` | 必要 | プロファイルの人のふるまいに近いかどうか。聴取者が自然と判断するかどうかを表すとは限らない |
| (c) 人の判断と照合した指標 | `score.pause_reaction_penalty`。内訳は `score.pause_no_reaction_rate`、`score.pause_barge_in_rate` | 必要 | 探索的な指標。構成は 1 回の聴取実験のデータで決めたもので、`measure` の事象検出の上での対応は独立に検証していない(7 節) |

`layers` の各層は `title`、`keys`(その層の主張を担う値)、`components`(内訳。単独では層の主張を担わない)、`note` を持つ。

## 2. 事象の定義

有声区間は `data/event_boundaries.py` の音量ベースの検出器(20 ms フレーム、ITU-T P.56 型の閾値。`detection.boundaries: audio` と同じもの)で取り、
0.3 秒以下の無音をつないで「発話区間」にする(`data/system_activity.py` と同じ)。発話区間を 1.0 秒以下の無音でつないだ連鎖を「ターン」と呼ぶ。

| 事象 | 定義(既定値) | 既定値の由来 |
|---|---|---|
| ユーザのターンの終わり | 1.5 秒以上のターンの終わり。直前 2.0 秒のシステムの有声が 0.5 秒以下で、応答の窓が録音内に収まるもの | 直前の条件は `detection.smooth_tt_roles` の定数。1.5 秒は短い発声の上限(下の注) |
| 応答 | ターンの終わりから −0.5〜+2.0 秒に始まる、最初の 0.2 秒以上のシステムの発話区間。遅延は符号つき | 応答の窓は Smooth TT の判定の窓、0.2 秒は `metrics/pause_response.py` |
| ターン内の休止 | 5.0 秒以上のターンの中の 0.4〜1.0 秒の無音で、休止の前後それぞれにターンが 1.5 秒を超えて続くもの | Pause の検出器の定数 |
| 休止の中の発声 | 休止と 0.1 秒以上重なるシステムの発話区間。1.5 秒以下 = 短い発声、それより長い = 長い発声 | 相槌とみなす長さの上限 1.5 秒、重なりの下限 0.1 秒 |
| ユーザの発話中の話し始め | ユーザの発話区間の内側で始まり、0.1 秒以上重なるシステムの発話区間 | 同上 |

注:

- ベンチマークの Smooth TT は「ユーザが 4 秒以上話したあと」に限っている。`measure` の既定は 1.5 秒(短い発声でなければターンの終わりとみなす)で、
  短い質問への応答も数える。`--set turn_min_seconds=4` にしても、ベンチマークの注釈の事象との一致は上がらない
  (実際の録音での検証では、一致は下がり、件数も減った。8 節)。既定は 1.5 のままにした。
- システムが話している最中に来たユーザのターンの終わり(直前 2.0 秒のシステムの有声が 0.5 秒を超える)は、応答の遅延を定義できないので数えない。
  その件数を `turn_end.skipped.system_speaking` に、割合を `turn_end.skipped_system_speaking_rate` に出す。
  割合の分母は、長さと録音の端の条件を満たしたターンの終わり(数えたもの + この理由で除いたもの)である。
  話し続けるシステムではこの割合が大きくなり、応答なしの割合と遅延は、残ったターンの終わりだけの値になる。
  割合が 0.3 以上のときは、解釈に注意を促す警告を 1 行出す(定数 `SYSTEM_SPEAKING_NOTICE`)。**0.3 は手で置いた目安で、検証した値ではない。**
- 休止の中の「短い / 長い」は**長さだけ**の判定である。転写が無いので、相槌かどうか、ターンを取ったかどうかは分からない。
- ターンの終わりの応答と、ユーザの発話中の話し始めは重なりうる(ユーザが話し終える直前の話し始め)。事象の一覧では `at_turn_end` で区別する。
- 閾値は `MeasureConfig` の項目(`--set KEY=VALUE`、検出器は `--set vad.margin_db=12` の形)で変えられる。未知の項目はエラーにする。
- 有声区間の閾値はチャネルごとの音量に対する相対値なので、誰も話していないチャネルでは雑音の大きい部分が「声」になる。
  これを防ぐため、`measure` は **−60 dBFS 未満のフレームを声としない**(`min_level_db`、`--set min_level_db=-70` で変更)。
  実際のシステム出力で確かめた範囲では、影響したのはほぼ無音の出力だけで、声のある録音の閾値はこの下限より十分に大きかった(2026-11-14)。
  発話のレベルが −45 dBFS を下回るような極端に小さい録音では、この下限を下げる必要がある。

## 3. ベンチマークの検出器との違い

| | ベンチマーク(`score-offline`) | `measure` |
|---|---|---|
| 事象の位置 | 評価セットの転写(文字の時刻)から検出し、全モデルで固定 | 録音ごとに、ユーザ側の音声の有声区間から検出 |
| ユーザ側の音声 | 人どうしの対話の片側(録音済み) | 録音の中の実際のユーザ |
| システムの応答の判定 | 既定は ASR の文字数と時刻(`system_activity: asr`) | 有声区間の長さだけ |
| 休止の反応の有声区間 | `metrics/pause_response.py` は 50 ms フレーム・ピーク比 5 % の検出器 | 20 ms フレーム・P.56 型の検出器 |
| クリップ | 20 秒 | 録音全体 |

このため、同じ名前の量でも値は一致しない。

## 4. どの変数をどこに記録するか

タイミングの数値は、モデル以外の多くの変数で動く。出力のどこに何を書くかを 3 つに分けた。

| 記録先 | 中身 | 誰が決めるか |
|---|---|---|
| `signature`(1 行の文字列) | ツールのバージョン、検出器と変更した設定、事象の設定、プロファイルの名前とハッシュ、チャネルの割り当て | ツールが自動で作る |
| プロファイルの `meta` | 規範を取った人どうしの録音の**言語・関係性・場面・媒体**、出典、録音数、事象数、検出の設定 | プロファイルを作る人(`make-profile` の必須引数) |
| `conditions` | 測った録音の側の条件: モデル、声、プロンプト(またはそのハッシュ)、回線、端末、収録日など | 測る人(`--condition key=value`、key は自由) |

`signature` は sacreBLEU の署名にならい、「同じ署名なら同じ手順」と言える範囲だけを入れる。例:

```
fdbja:0.2.0.dev0|measure|vad:energy(p56)|events:default|profile:none|ch:user=0,sys=1
fdbja:0.2.0.dev0|measure|vad:energy(p56;margin_db=12.0)|events:custom(turn_min_seconds=4.0)|profile:ja-strangers-chat-video_call@06dde326|ch:user=1,sys=0
```

`conditions` は署名に入れない(自由記述で、手順ではなく対象の説明だから)。出力には必ず残る。
プロンプトのように中身を出したくないものは `--condition-file prompt=prompt.txt` で `sha256:<先頭 12 桁>` だけを記録する。

言語・関係性・場面・媒体をプロファイル側に置いたのは、これらが「何を自然とみなすか」(規範)を決める変数だからである。
初対面の雑談と窓口の応対、対面と通話では、人どうしの交替の遅延も重なりの量も違う。規範を 1 つに固定せず、差し替えられるものにした。

## 5. リーダーボードの数値と取り違えないための決まり

- 出力のキー名を `results.json` / `summary.json` と重ねない。`TOR`、`pause_response`、`pause_no_response_rate`、`pause_interrupt_rate`、
  `lat_median`、`overlap_rate` は使わず、`turn_end.response_rate`、`turn_end.latency_median`、`pause.voiced_rate`、
  `pause_no_reaction_rate`、`pause_barge_in_rate` などにした(単体テストで重なりが無いことを確認している)。
- `measure` の JSON には `summary.json` の欄(システムごとの行)が無いので、`leaderboard` コマンドに渡しても行は出ない。
- 表示と JSON の両方に「リーダーボードとは比較できない」旨を必ず入れる(`comparability`)。
- `signature` の 2 番目の欄を `measure` にして、ベンチマークの採点条件(`summary.json` の `conditions`)と形を変えた。

## 6. 基準プロファイル

形式は `fdbja-profile/1` の JSON 1 つ。

```json
{
  "format": "fdbja-profile/1",
  "name": "ja-strangers-chat-video_call",
  "meta": {"language": "ja", "relationship": "strangers", "situation": "chat", "medium": "video call",
           "source": "...", "n_recordings": 12, "n_events": {"turn_ends": 0, "responses": 0, "pauses": 0},
           "detection": {"...": "measure の設定の全項目"}, "fdbja_version": "..."},
  "norms": {"response_latency": {"low": 0.0, "high": 0.0, "basis": "percentiles 5 and 95 of the human response latency"},
            "pause": {"...": "休止の反応のルールの閾値"}},
  "reference": {"...": "人どうしの録音の記述統計(measure の stats と同じ構成)"},
  "reference_score": {"basis": "...", "note": "...",
                      "latency_in_tolerance_rate": 0.0, "latency_deviation_mean": 0.0,
                      "turn_end_no_response_rate": 0.0, "n_turn_ends": 0,
                      "pause_no_reaction_rate": 0.0, "pause_barge_in_rate": 0.0,
                      "pause_reaction_penalty": 0.0, "n_pauses": 0}
}
```

(上の数値は形式の説明用で、実測値ではない。)

- **`generic`(同梱はこれだけ)**: ツールのルール定数だけからコードの中で作る。録音を 1 本も使っていないので、**人の対話のデータに基づく規範ではない**。
  許容範囲は応答の窓(−0.5〜+2.0 秒)そのものなので、`latency_in_tolerance_rate` は応答ありの割合と同じ値になり、
  `latency_deviation_mean` は常に 0 になる。意味があるのは休止の反応の 2 つの割合だけである。
- **`make-profile`**: 人どうしの 2 チャネル録音のディレクトリから作る。各録音を**両方向**(ch0 をユーザ、ch1 をユーザ)で測って合わせる。
  許容範囲は人の応答の遅延の 5〜95 パーセンタイル(`--tolerance` で変更可)。言語・関係性・場面・媒体は必須引数である。
  応答が 30 件に満たないときは警告を `meta.warnings` に残す(30 は目安で、根拠のある値ではない)。
- プロファイルは自分の検出の設定(`meta.detection`)を持つ。`measure` に設定を渡さなければプロファイルの設定で測るので、
  規範と測定の検出条件がそろう。設定を別に渡して食い違ったときは警告を出す。
- **基準の録音自身の採点値(`reference_score`)**: `make-profile` は、プロファイルを作った録音そのものを、同じ検出の設定で(両方向で)測り、
  できたプロファイルで採点した値を `reference_score` に保存する。キーは `score` と同じである
  (許容範囲に入った割合、範囲からの外れ、応答なしの割合、休止の無反応・割り込み・その和、件数)。
  `measure --profile` は各スコアの横にこの値を並べて表示し、JSON では `score.reference_score` に入れる。
  スコアは値だけでは良し悪しが分からない(人どうしの録音でも、許容範囲に入った割合は 1 に届かず、休止の指標は 0 にならない。8 節)ので、
  人の録音の値を目安として並べる。
  **これは同じ録音での値で、楽観的な目安である**(許容範囲をその録音自身から決めているので、別の録音で確かめた値ではない)。
  このことは JSON の `reference_score.basis` と `reference_score.note` にも書いてある。
  別の録音での値が要るときは、録音を 2 組に分けて片方でプロファイルを作り、残りを `measure --profile` で測る。
- `reference_score` の無いプロファイル(この欄を足す前のバージョンで書いたもの)も、そのまま読める。`generic` にもこの欄は無い(`null`)。
  そのときは横の値を表示しない。古いプロファイルには、作り直しを勧める注記を `score.note` に入れる。
  形式名は `fdbja-profile/1` のままにした(欄を足しただけで、既存の欄は変えていない)。
- 特定のコーパスから作った統計は同梱しない(ライセンスと、規範を 1 つに固定しないため)。プロファイルは利用者が作って配る。

## 7. スコア: 2 つの層と、人の判断で検証した 2 指標との関係

README「提案指標」の 2 つのうち、音声だけで計算できる部分だけを使った。

| 指標 | 必要なもの | `measure` での扱い |
|---|---|---|
| 境界重み付き VAP-distance | 予測器(extra とチェックポイント)と、**同じ事象に対する人の応答** | 使わない。任意の録音には人の参照が無く、定義上計算できない |
| 割り込みと無反応を罰する Pause 指標 | 休止の区間と、休止の前後のシステムの有声区間 | ルール(`judge_event`)をそのまま、ここで検出した休止に適用する |

スコアは 1 節の層 (b) と層 (c) に分かれる。

**層 (b): 人の規範からの外れ**

- ベンチマークに「人の許容範囲に照らした遅延の指標」は実装されていない(Smooth TT は二値の TOR と遅延の分位点)。
  `measure` では `latency_in_tolerance_rate`(応答の遅延がプロファイルの許容範囲に入ったターンの終わりの割合)と
  `latency_deviation_mean`(許容範囲からの外れの平均、秒。範囲内は 0 とし、応答のあったターンの終わりで平均する)を新しく置いた。
- **応答なしは許容範囲の外として数える。** `latency_in_tolerance_rate` の分母は数えたターンの終わりの全部で、応答の無かったものは範囲外の側に入る。
  その割合を `turn_end_no_response_rate`(`stats` の `turn_end.no_response_rate` と同じ値)として内訳に出し、表示にも範囲外に数えたことを書く。
- この層が表すのは「プロファイルの人のふるまいに近いか」であり、「聴取者が自然と判断するか」を表すとは限らない。
  実際の録音での検証では、5〜95 パーセンタイルの許容範囲に入った割合は聴取の結果と対応しなかった(8 節)。**人の判断と照合した指標ではない。**

**層 (c): 人の判断と照合した指標(探索的)**

- 休止については `pause_no_reaction_rate`(休止に反応しなかった割合)、`pause_barge_in_rate`(休止の中で話し始めてユーザの再開後も 0.5 秒以上話し続けた、または休止の直前 2 秒にユーザと 0.5 秒を超えて重なっていた割合)、
  `pause_reaction_penalty`(2 つの和。0〜2、小さいほどよい)を出す。ルールは同じだが、事象と有声区間の検出器が違う(3 節)ので、
  掲載の `pause_response` とは**別の量**として別名にした。
- この層の主張を担うのは和の `pause_reaction_penalty` だけで、2 つの割合は内訳である。
  実際の録音での検証で、システム間の順位が聴取の結果と対応したのは、`measure` の値の中ではこの和だけだった(8 節)。
- **探索的な指標である。** 構成(無反応と割り込みの和)は 1 回の聴取実験のデータで決めたものである。
  `measure` の事象検出の上での聴取との対応も、その同じ聴取実験のデータで見たものなので、独立には検証していない。
- 値だけでは良し悪しが分からない。人どうしの録音でも、休止の多くに相手は反応しないので値は 0 から遠く、何も話さない出力の値との差は小さい。
  プロファイルの `reference_score` の値と並べて解釈する(6 節)。

## 8. 検証で分かった制約

評価セットの録音(人どうしの録音と、複数のシステムの出力)を `measure` で測り、注釈の事象、掲載値、聴取の結果と比べた。
公開前のデータに由来するので、数値はここに載せない。分かったことは次のとおり。

1. **検出器は信用できるが、事象の集合はベンチマークの注釈と一致しない。**
   有声区間の時刻のずれは、時刻の分かっている合成信号で 1 フレーム以内に収まり、検証した録音では雑音が原因の誤りは少なかった。
   一方、`measure` が検出する休止とターンの終わりは、注釈の事象の一部しか拾わず、検出の大半は注釈に無い事象だった。
   原因は検出の誤りではなく定義の差である(転写の「発話」は音声上の無音を含む。注釈は相手の人のふるまいも条件にして事象を選んでいる)。
   `turn_min_seconds`、無音の長さの上限、検出器の閾値のどれを変えても解消しない。
   **`measure` の値を、掲載値と同じ水準の数値として並べてはいけない**(5 節)。
   システム間の順位は多くの値で掲載値と対応したが、値の水準は対応しない
   (応答の速いシステムの速さが遅延の値に表れない、休止の中の長い発声の割合が掲載の TOR より小さく出る、など)。
2. **聴取の結果と対応したのは `pause_reaction_penalty` だけだった。**
   休止で発声した割合、応答なしの割合、許容範囲(5〜95 パーセンタイル)に入った割合は対応しなかった。
   ただし、この指標の構成は同じ聴取実験のデータで決めたものなので、独立な検証ではない(7 節)。比べたシステムの数も少ない。
3. **許容範囲に入った割合は、遅いシステムを区別しない。**
   5〜95 パーセンタイルの範囲は広く、応答が人よりはっきり遅いシステムが、人どうしの録音より高い値になった。
   範囲を狭くする案はあるが、同じ聴取データでの事後の選択になるので、独立なデータで確かめるまで既定は変えない(10 節)。
4. **人どうしの録音を同じ方法で採点しても、スコアは上限や下限に届かない。**
   応答なしを範囲外と数え、許容範囲は定義上、人の遅延の両端を除くので、許容範囲に入った割合は 1 に届かない。
   休止の指標も、人どうしの録音の値と、何も話さない出力の値との差が小さい。
   このため、プロファイルに基準の録音自身の採点値を持たせ、スコアの横に並べることにした(6 節)。
5. **話し続けるシステムでは、ターンの終わりの多くが「話中」として除かれる。**
   常に話している出力では数えられるターンの終わりが無くなり、そうでないシステムでも少なくない割合が除かれた。
   除いた割合を見ないと、応答なしの割合と遅延を誤って解釈するので、割合を統計として出すことにした(2 節の注)。
6. **確かめていない条件。** 検証した録音は、話者ごとにチャネルが分かれた、雑音の少ない短いクリップである。
   雑音や音漏れのある録音(マイクでの収録、スピーカーの音の回り込み)と、長い録音では検証していない。

## 9. 限界

1. 音量ベースなので、発話と雑音・笑い・息・咳を区別しない。システム側の合成音声の無音区間に雑音が乗る録音では有声が増える。
2. チャネル間の音漏れ(スピーカーの音をマイクが拾う)があると、重なりと話し始めが過大になる。エコー除去後の、話者ごとに分かれた録音が前提。
3. 相槌とターンを取る発話を長さだけで分けている。短い応答(「はい」だけ)は短い発声に、長い相槌は長い発声に数えられる。
4. ターンの終わりは無音の長さ(1.0 秒)で決めている。言い淀みの長い話者では、1 つのターンが 2 つに割れる。
5. 録音の末尾のターンの終わりは、応答の窓が録音内に収まらなければ数えない(`skipped` に件数が残る)。
6. 既定値は、合成信号の単体テストと、雑音の少ない短い録音での検証(8 節)で確かめただけである。
   検出する事象はベンチマークの注釈の事象と一致しない。雑音や音漏れのある録音と、長い録音では未確認。
7. 録音どうしの比較は、ユーザ側の話し方がそろっているときに限って意味を持つ。ユーザが違えば事象の分布も違う。

## 10. 未決事項

- 許容範囲の決め方。5〜95 パーセンタイルは遅いシステムを区別しない(8 節)。範囲を狭くする案と、遅延の分布そのものを比べる量(分布間の距離)に
  替える案があるが、独立なデータ(別の聴取実験か別のコーパス)で確かめてから決める。
- `pause_reaction_penalty` と聴取の結果との対応を、構成を決めたのとは別の聴取実験で確かめること。
- 「話中」で除いた割合の警告の閾値(`SYSTEM_SPEAKING_NOTICE`、いまは手で置いた 0.3)。
- `pause_reaction_penalty` を、掲載の `pause_response` と同じ 50 ms・ピーク比 5 % の検出器でも計算できるようにするか。
- ターン内の休止とする無音の長さの上限(`pause_max_gap`)。長くすると注釈の休止を拾う割合は少し上がるが、注釈に無い事象も増える。聴取との対応は未確認。
- mono の組が並んだディレクトリ(`*_user.wav` / `*_system.wav`)の受け取り方。いまは 2 チャネルのファイルだけ。
- プロファイルを配る場所と、名前の付け方の決まり。
- `measure` の数値を載せる場所を作るか(作る場合も、リーダーボードとは別の表にする)。

## 11. 予測器を使う指標を `measure` に足す場合(設計メモ、未実装)

`metrics/turnnat.py` の尤度のスコアは人の参照を必要としないので、任意の録音に適用できる唯一の予測器ベースの量である。
現状はライブラリの関数(`turnnat_score`)と単体テストだけがあり、コマンド・設定・採点の経路からは呼ばれていない。
予測器の出力(256 クラスの確率の系列)を引数に取るので、動かすには extra `vap` とチェックポイントが要る。
ファイル内の有声区間・境界・集計の関数は numpy だけで動く。

足す場合に決めること:

1. **チェックポイントの取得**: いまは README の手順で、リビジョンを固定した URL から手で取り、SHA-256 を照合している。
   自動化するなら (a) 取得先とリビジョンとハッシュを 1 か所の表に持ち、(b) 利用者のキャッシュディレクトリに置き、(c) ハッシュが合わなければ使わない、
   (d) 明示の指示(コマンドか引数)があったときだけ取得し、`measure` の既定の経路では何も取得しない、の 4 点を守る。
   チェックポイントごとにライセンスが違う(非商用のものがある)ので、表にライセンスを並べ、取得時に表示する。
2. **署名**: 予測器の名前とハッシュを `signature` に入れる(`…|predictor:<名前>@<ハッシュ>`)。予測器が違えば値は比べられない。
3. **解釈**: 尤度は「予測器の学習データらしくない」ことしか言わない。プロファイルの言語・場面と予測器の学習データが違うときの扱いを先に決める。
4. **人の判断との照合**: 載せる前に、聴取の結果と照合する。照合前は「実験的」と表示する。
