# 対話の条件ごとに測る(`fdbja measure-contexts`)の設計

状態: 実装済み(`src/fdbja/contexts.py`、`fdbja measure-contexts`、Python では `fdbja.measure_contexts`)。
確かめたのは合成信号の単体テストまでで、**実際の録音ではまだ確かめていない**(8 節)。
採点の定義・既定値・`docs/` の掲載値には影響しない。`measure` の出力も変わらない。

## 0. 位置づけ

`measure`([measure-entry.md](measure-entry.md))は、1 組の録音を 1 つの基準プロファイルと比べる。
しかし、適切なタイミングは 1 つではない。対話のタスク、場面、話者どうしの関係、システムのペルソナで変わる。
人どうしの対話でも、条件が違えば応答の遅延も声の重なりの量も違う。

そこで問いを 2 つに分ける。

1. **条件ごとの近さ**: その条件の人どうしの録音と比べて、システムの値はどれだけ離れているか。
2. **条件への追従**: 条件が変わったとき、人どうしの録音の値が動く向きに、システムの値も動くか。

1 は `measure --profile` を条件ごとに呼んでも分かる。2 は条件をまたいで比べないと分からない。
どの条件でも同じタイミングで話すシステムは、1 ではある条件で近く見えても、2 では「変化なし」になる。
`measure-contexts` は 1 と 2 を同じ単位(録音)と同じ検出の設定で出す。

**聴取者の判断との照合はしていない**。出るのは人どうしの録音のふるまいとの比較だけである(6 節)。

## 1. 用語

- **条件(context)**: 対話が何であるか。タスク、場面、関係、ペルソナなど。名前は利用者が付ける(`chat`、`interview` など)。
  何を変えたかは `--factor` に書き、出力にそのまま写す(値の計算には使わない)。
- `measure` の `--condition`(`conditions`)は、録音をどう取ったか(モデル名、声、日付など)の自由記述で、これとは別のものである。
- **変化(shift)**: 条件 A から条件 B への値の差(B − A)。
- **差(gap)**: 同じ条件での、システムの値 − 人どうしの録音の値。

## 2. 入力と出力

```
fdbja measure-contexts NAME=RECORDINGS [NAME=RECORDINGS ...] [--profile NAME=PROFILE ...]
                       [--factor F] [--baseline NAME] [--set KEY=VALUE ...]
                       [--bootstrap N] [--seed S] [--user-channel C] [--system-channel C] [--json OUT]
```

- `NAME=RECORDINGS`: 条件の名前と、その条件でのシステムの録音(2 チャネルの wav か、そのディレクトリ)。同じ名前を繰り返すと経路を足す。
- `--profile NAME=PROFILE`: その条件の人どうしの録音から `make-profile` で作ったプロファイル。条件ごとに 1 つ。
- 条件は 2 つ以上要る。プロファイルだけの条件、録音だけの条件があってもよい(無い側の値は出さない)。
- 条件の組は、既定では全部の組(渡した順)。`--baseline NAME` を付けると、その条件とほかの条件の組だけにする。
- 検出の設定は全条件で同じにする。`--set` が無ければプロファイルの `meta.detection` を使い、プロファイルどうしで違えばエラーにする。
  `--set` を渡してプロファイルの設定と食い違ったときは警告を出す。

出力(`--json`、形式名 `fdbja-contexts/1`)の主な欄:

| 欄 | 内容 |
|---|---|
| `contexts.<名前>` | 録音数、`measure` と同じ `stats` / `score` / `signature` / `quality`、プロファイルの識別子と `meta`、`features` |
| `contexts.<名前>.features.<量>` | `system` / `human`(`value` = 録音にわたる平均、`n` = 値のある録音の数、`interval`)と `gap` |
| `shifts[]` | `from` / `to` と、量ごとの `human` / `system` の変化(`value`、`interval`、`clear`)、`verdict`、`ratio` |
| `summary` | 判定ごとの件数、条件の組の数、`followed_rate`(人どうしの録音に変化のあった量のうち `followed` の割合) |
| `layers` | 3 つの層(`context_gap`、`context_shift`、`listener_judgement`)が何を表し、何と照合したか(していないか)の説明 |
| `bootstrap`、`config`、`warnings` | 区間の設定、検出の設定、警告 |

`comparability` には `measure` と同じ「リーダーボードとは比較できない」の文を入れる。

## 3. 録音ごとの値

分析の単位は録音である。1 つの対話の中の事象(ターンの終わり、ポーズ)は互いに独立ではないので、事象を単位にして区間を出すと狭くなりすぎる。
そこで、録音ごとに次の値を 1 つずつ出し(`fdbja.measurement.recording_features`)、条件の値はその平均とする。

| 名前 | 内容 | 条件の間で比べるか |
|---|---|---|
| `latency_median` | ターンの終わりからシステムが話し始めるまでの時間の中央値(秒) | 比べる |
| `no_response_rate` | ターンの終わりのうち、応答が無かった割合 | 比べる |
| `starts_in_user_speech_per_minute` | ユーザの発話中にシステムが話し始めた回数(ユーザの発話 1 分あたり) | 比べる |
| `overlap_share` | 両者が同時に声を出していた時間の、録音に占める割合 | 比べる |
| `pause_voiced_rate` | ユーザのターン内のポーズのうち、システムが声を出した割合 | 比べる |
| `pause_reaction_penalty` | ポーズでの無反応の割合 + 割り込みの割合 | 比べない(6 節) |

- 事象の定義は `measure` と同じである(measure-entry.md の 2 節)。
- 事象が無くて値を出せない録音は、その量では数えない(`n` が減る)。
- 人どうしの録音は、`make-profile` と同じく両方向(ch0 をユーザ、ch1 をユーザ)を合わせて、録音 1 本につき 1 行にする。
- 録音にわたる平均なので、長い録音も短い録音も同じ重みになる。条件ごとの表の下に出る `measure` の値(全録音の事象をまとめた値)とは一致しないことがある。

量をこの 6 つにしたのは、`measure` の記述統計のうち、録音 1 本から出せて、タイミングの主な側面(応答の速さ、応答の有無、
割り込み、重なり、ポーズでの発声)を 1 つずつ表すものを選んだためである。聴取者の判断との対応で選んだものではない(8 節)。

## 4. 区間と判定

- **区間**: 録音を単位にした percentile bootstrap(95 %、既定 2,000 回)。録音を復元抽出して平均を取り直す。
  変化(B − A)と差(システム − 人)は、2 つの側を独立に抽出して差を取る(2 組の録音は別々の対話なので、対にはしない)。
- **録音が少ないとき**: その量の値がある録音が 5 本に満たない側があれば、区間を出さない。5 は percentile の区間が意味を持つための目安で、
  確かめた値ではない(`FEW_RECORDINGS`)。
- **乱数**: 条件・側・量ごとに別の系列を使う(seed と、名前から作った値で初期化)。条件を足したり順番を変えたりしても、ほかの条件の区間は変わらない。
- **「変化がある」**: 変化の区間が 0 を含まないこと(`clear`)。
- **判定**(量ごと、条件の組ごと):

  | 人どうしの録音 | システム | 判定 |
  |---|---|---|
  | 変化あり | 同じ向きの変化あり | `followed` |
  | 変化あり | 逆向きの変化あり | `opposite` |
  | 変化あり | 区間が 0 を含む | `no_clear_system_shift` |
  | 区間が 0 を含む | 変化あり | `system_only` |
  | 区間が 0 を含む | 区間が 0 を含む | `no_clear_human_shift` |
  | どちらかの区間が出せない | | `not_assessed` |

- **`ratio`**: 人どうしの録音に変化があるとき、システムの変化 ÷ 人どうしの録音の変化。1 なら同じ大きさ、0 なら変化なし、負なら逆向き。
  区間は付けていない(8 節)。
- **まとめ**: 人どうしの録音に変化のあった量のうち、`followed` だった数と割合。量どうしは独立ではない(応答が遅くなれば重なりは減る)ので、
  この割合は目安であって、単独のスコアとして順位づけに使うことは想定していない。

判定を「同じ向きに動いたか」に留め、「同じ大きさだけ動いたか」を合否にしなかったのは、人どうしの録音の変化の大きさがそのまま
システムの目標になるとは言えないからである(人と同じ大きさで動くことを聴取者が好むかは確かめていない)。大きさは `ratio` と条件ごとの差で見る。

## 5. プロファイルに足した欄

人どうしの録音の側でも録音を単位にした区間を出すには、録音ごとの値が要る。そこで `make-profile` が `reference_recordings` を書くようにした。

- 録音 1 本につき 1 行、3 節の 6 つの数値だけを持つ。**ファイル名も音声も入らない**。行の順は、経路を並べ替えた順である。
- 形式名は `fdbja-profile/1` のままにした(欄を足しただけで、既存の欄は変えていない)。
- この欄の無いプロファイル(足す前に書いたものと `generic`)も読める。`measure` の動作は変わらない。
  `measure-contexts` では、その条件の人どうしの録音の値を出さず、`make-profile` での作り直しを案内する警告を出す。
- プロファイルを配るとき、録音ごとの値が入ることを問題にする場合は、この欄を消して配ってもよい(`measure` はそのまま使える)。

## 6. 言えること・言えないこと

- **言えること**: 同じ検出の設定で測ったとき、(a) ある条件で、システムの値がその条件の人どうしの録音の値からどれだけ離れているか、
  (b) 2 つの条件の間で、人どうしの録音の値が動いた向きにシステムの値が動いたか。
- **聴取者の判断について**: 何も言えない。どの値も聴取者の判断と照合していない。
  `pause_reaction_penalty` はこのベンチマークの評価セットの上で第三者の聴取者の判断と照合した指標だが、その照合は 1 種類の対話の上だけで行った。
  聴取者の判断が条件で変わるか(たとえば、ある場面では間を置くほうが好まれるか)は確かめていない。
  そのため、この量は条件ごとに値を出すだけにして、条件の間の判定は付けない。
- **変化の原因について**: 2 つの条件の間の変化には、2 組の録音の間のあらゆる違いが入る。ユーザが違えば話す速さも間の取り方も違い、
  システムの値はユーザのふるまいに引きずられる。システムの変化をシステムのふるまいの違いとして解釈できるのは、
  ユーザ側の音声をそろえ、システムへの指示(ペルソナ、タスクの説明)だけを変えて録ったときである(7 節)。
- **区間について**: 比較 1 つごとの区間で、比較の数に対する補正はしていない。5 つの量 × 条件の組の数だけ比較があるので、
  偶然 0 を外れる区間も出る。逆に、区間が 0 を含むことは、変化が無いことの証拠ではない。
- **録音の条件について**: `measure` の制約(雑音、チャネル間の音漏れ、クリップ、録音レベル。measure-entry.md の 8 節と README の「対応する録音条件」)がそのまま当てはまる。
  条件によって収録の環境が違うと、その違いが変化として出る。録音の品質の警告は条件の名前を付けて `warnings` に出す。

## 7. 録音の集め方(推奨)

実装が決めていることではなく、6 節の制約から導いた勧めである。

1. **人どうしの録音**は、条件ごとに 5 本以上(区間を出す最低限)。話者の組が違う録音を集める(同じ 2 人の録音ばかりだと、その 2 人の癖が規範になる)。
2. **システムの録音**は、条件ごとに 5 本以上。条件の間でユーザ側をそろえられるなら、そろえる。
   - 人が相手をする収録: 同じ人たちが両方の条件でシステムと話す。
   - 録音済みのユーザ音声を流す収録: 同じユーザ音声に対して、システムへの指示だけを変える。このとき変化はシステムだけの違いになるが、
     ユーザがシステムに合わせて話し方を変える効果は入らない。
3. 収録の環境(マイク、エコー除去、媒体)は条件の間でそろえる。
4. 条件の数は、先に決めた比較に絞る。条件を増やすほど比較が増え、偶然の「変化あり」が増える。

## 8. 未決事項

- **実際の録音での確認**。条件の違う人どうしの録音(雑談とタスクのある対話など)で、人どうしの録音の変化が区間つきで出るか、
  5 本という下限が妥当か、録音の長さがどれだけ要るかを確かめる。
- **聴取者の判断との照合**。条件ごとに聴取実験を行い、聴取者が自然と判断するタイミングが条件で変わるか、変わるならこの表の変化と対応するかを確かめる。
  それまでは、ここで出る値は「人どうしの録音への近さ」に留まる。
- **量の選び方**。いまの 6 つは `measure` の記述統計から選んだもので、条件による違いを最もよく表す量かは確かめていない。
  遅延の分布の広がり(中央値だけでなく)、相槌の頻度、発話の長さを足すかどうか。
- **比較の数に対する補正**。補正した区間を既定にするか、補正前と補正後の両方を出すか。
- **`ratio` の区間**。分母(人どうしの録音の変化)が 0 に近いと不安定になるため、いまは点推定だけを出している。
- **ユーザ側をそろえた収録の扱い**。同じユーザ音声で条件を変えた録音は対になるので、対の差で区間を出すほうが狭くなる。
  対を指定する入力(対応表)を足すかどうか。
- **条件の記述の決まり**。いまは名前と `--factor` だけで、条件の中身(タスクの説明、ペルソナの文、関係)は記録しない。
  複数の変数(タスク × 関係など)を持つ対応表(manifest)を受け取るかどうか。
- **コマンドと用語の名前**(`measure-contexts`、「条件」)。`measure` の `--condition` と紛らわしくないか。
- **プロファイルを配るときの `reference_recordings` の扱い**(5 節)。
